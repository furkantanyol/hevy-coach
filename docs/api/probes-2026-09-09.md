# Live API probes, 2026-09-09

Run against `https://api.hevyapp.com/v1` with the owner's key, using curl. Account was on the **Free** plan at probe time (reads worked anyway, see "Plan limits"). Spec reference: `hevy-openapi.2026-09-09.json` in this directory.

## 1. pageSize maximums

| Endpoint | 10 | 11 | 50 | 100 | 101 | Error body |
|---|---|---|---|---|---|---|
| GET /workouts | 200 | 400 | 400 | 400 | 400 | `{"error":"pageSize must be less than or equal to 10"}` |
| GET /workouts/events | 200 | 400 | 400 | 400 | 400 | same |
| GET /routines | 200 | 400 | 400 | 400 | 400 | same |
| GET /routine_folders | 200 | 400 | 400 | 400 | 400 | same |
| GET /body_measurements | 200 | 400 | 400 | 400 | 400 | same |
| GET /exercise_templates | 200 | 200 | 200 | 200 | 400 | `{"error":"pageSize must be less than or equal to 100"}` |

The spec declares no `maximum` for any of these. Limits are enforced server-side only.

All list responses carry `{ page, page_count, <items> }`. `page_count` is total pages at the requested size.

## 2. exercise_history shape

Confirmed **flat**, one row per set, newest workout first, sets in workout order:

```json
{"workout_id":"…","workout_title":"2 Lower A","workout_start_time":"2026-09-07T16:32:48+00:00","workout_end_time":"2026-09-07T17:42:08+00:00","exercise_template_id":"D04AC939","weight_kg":85,"reps":7,"distance_meters":null,"duration_seconds":null,"rpe":8.5,"custom_metric":null,"set_type":"normal"}
```

Not paginated. 275 rows returned for one template. The pre-1.0 client type (`{start_time, sets[]}`) was wrong and `get-exercise-progression` throws on it.

## 3. Workout events

- Order: newest `updated_at` first.
- Updated event: `{"type":"updated","workout":{…full Workout…}}`.
- Deleted event, verified 14:24 CEST after deleting a workout in the app: `{"type":"deleted","id":"ba0f0022-…","deleted_at":"2026-09-09T12:24:34.682Z"}`. Matches the spec. It surfaces in `GET /workouts/events?since=…` immediately and `workouts.changes()` places it in `deletes` with `deleted_at` as the cursor.
- `since=1970-01-01T00:00:00Z` returns every workout as an `updated` event (28 pages of 10 here, same as the workout count), so it is a valid full-sync bootstrap.
- Workout `updated_at` in events uses `.sssZ` ms precision; `start_time` on workouts uses `+00:00` offset form. Both parse as ISO 8601.

## 4. exercise_history date filters

| `start_date` | Status | Rows |
|---|---|---|

## 5. rest_seconds

Live routine responses return `rest_seconds` as a **number** on every exercise across all routines. The spec's `type: "string"` is a spec bug. `rep_range` is absent from routine set responses when not set (key omitted, not null).

## 6. Response shapes that differ from the code's types

- `Workout` has `routine_id` (string), no `is_private` key in responses.
- `RoutineFolder` has `index`.
- `BodyMeasurement` responses include `id` (number) and `created_at`; absent fields are omitted, not null.
- `GET /user/info` returns `{ data: { id, name, url } }`.
- Not-found bodies are inconsistent: `GET /workouts/{id}` and `GET /exercise_templates/{id}` return **plain text** (`Workout not found`), `GET /routines/{id}` returns JSON `{"error":"Routine not found"}`. The client must not assume JSON on error responses.

## 7. Rate limits

- No `ratelimit-*`, `retry-after`, or `x-request-id` headers on any 200 or 4xx.
- Burst of 60 parallel `GET /workouts/count`: 60 × 200. Could not trigger a 429 cheaply. Server is Heroku, Express behind it, `access-control-allow-origin: *`.
- Client policy: retry on 429 and 5xx and network errors with backoff and jitter, honouring `retry-after` if it ever appears.

## 9. Plan limits and write probe

`POST /v1/routines` on this Free account returned **409** (spec says 403):

```json
{"error":"routine-limit-exceeded","message":"Free accounts are limited to 4 routines. Upgrade to Hevy Pro (https://hevy.com/plans) to create more."}
```

Consequences:

- The `[TEST] hevy-coach probe` routine could not be created, so the `folder_id` on `PUT /routines/{id}` check and the live idempotent-write check are **blocked** until a routine slot exists or the account is Pro. The live spec says PUT accepts nullable `folder_id`; the client will send it and tests will mock it.
- Reads, exercise_history, events, and webhook endpoints all work on a Free account despite the docs saying Pro only.
- Error envelope for limit errors is `{ error: <code>, message: <human text> }`. Other 4xx use `{ error: <text> }` or plain text.

## 9b. Routine write probe (re-run on Pro, 2026-09-09 13:51 CEST)

After upgrading the account to Pro the `[TEST] hevy-coach probe` routine was created (id `6886475a-…`) and used for every check below.

| Check | Result |
|---|---|
| `POST /routines` response | 201, body is `{ routine: Routine }` (spec says bare `Routine`) |
| `PUT /routines/{id}` response | 200, body is `{ routine: Routine }` (spec says bare) |
| PUT with `folder_id: null` | moves the routine to "My Routines" (`folder_id` becomes null) |
| PUT with `folder_id: 3586017` | moves it into that folder |
| PUT **omitting** `folder_id` | keeps the current folder (not reset to null) |
| PUT with an unknown `folder_id` | 400 `{"error":"Invalid routine folder id: 1"}` |
| Identical PUT twice | content unchanged; `updated_at` bumps on every PUT |
| `rpe` on a routine set | 400 `Unrecognized key(s) in object: 'rpe'` (RPE is workout-only) |
| POST with a title that already exists | 201, duplicate created (titles are not unique) |

Consequences: `update-routine` must omit `folder_id` unless the caller sets it; the client unwraps both bare and wrapped routine responses; routine set schemas must not accept `rpe`. The duplicate-title check created a second routine, renamed to `[TEST] hevy-coach probe (duplicate, safe to delete)`; delete both `[TEST]` routines in the app when done (the API has no DELETE).

## 10. RPE values (spec)

`PostWorkoutsRequestSet.rpe` is an enum: `6, 7, 7.5, 8, 8.5, 9, 9.5, 10`. There is no 6.5. The client's `Rpe` type and the MCP `create-workout` schema follow the spec.
